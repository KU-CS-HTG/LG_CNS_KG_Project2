# 작업 항목 (기능 단위 진행 방식)

> 2026-10-26부터 팀은 A·B·C 영역을 나누지 않고 **기능 단위**로 일한다. 이 문서는 지금 구현해야 할 기능 목록이고,
> 새 기능이 생기면 여기에 먼저 적는다. 디렉터리별 담당 표는 더 이상 작업 범위를 제한하지 않는다 (CLAUDE.md 갱신은 팀 합의 후).

## 1. 진행 방식

1. **시작 전에 적는다.** 이 문서에 항목(무엇을·왜·끝났다는 기준·건드릴 파일)을 먼저 올리거나 이미 있는 항목에 "내가 한다"고 표시한다. 같은 일을 둘이 하지 않기 위해서다.
2. **`main`을 pull하고 시작한다.** `git checkout main && git pull`, 그 위에서 기능 브랜치를 만든다 (`feat/<항목번호>-<짧은이름>`).
3. **기능 하나 = 브랜치 하나 = PR 하나.** 한 PR이 여러 기능을 섞지 않는다. 데이터 파일(검수 결과 등)은 코드 PR과 따로 올린다.
4. **끝났다는 기준은 숫자나 눈으로 확인할 수 있어야 한다.** 각 항목의 "완료 기준"을 PR 설명에 그대로 옮기고 결과를 적는다.
5. **여러 사람이 같이 쓰는 파일은 먼저 알린다.** 특히 `src/common/schema.py`, `src/retrieve/hybrid.py`, `src/generate/generator.py`, `app/main.py`, `requirements.txt`. 같은 파일을 두 항목이 고치면 먼저 올라간 쪽 기준으로 나중 쪽이 합친다.
6. **지표를 바꾸는 변경은 전후 숫자를 같이 적는다.** 검색은 `python -m eval.run_eval --questions reviews/exports/dev_v2.jsonl --experiment hybrid_filter --k 5`, 같은 시험지·같은 기준일로 비교한다.
7. 설계가 바뀌면 `docs/ARCHITECTURE.md`와 CLAUDE.md 해당 절, 기획서 8.3도 같은 PR에서 고친다 (기존 문서 동기화 규칙 그대로).

## 1.1 시작 순서와 공통 규칙 (W1~W4)

- **0단계**: 기반 PR(필드·자리표시자, #31)이 `main`에 병합되기 전에는 시작하지 않는다. 병합 후 모두 `git checkout main && git pull`, 각자 `main`에서 자기 브랜치를 만든다.
- 위 "고치는 파일"에 없는 파일은 고치지 않는다. `schema.py`, `app/main.py`, `generator.py`에는 호출 자리가 이미 있다.
- 새 테스트는 새 파일에 쓴다 (`test_generate.py`를 고치지 않음).
- README·ARCHITECTURE·CLAUDE.md는 기능 PR에서 고치지 않고 PR 설명에 "문서에 넣을 내용"만 적는다. 모두 병합된 뒤 한 명이 문서 PR 하나로 모은다.
- 하루 한 번과 PR 올리기 전에 `git merge origin/main`. PR은 기능 하나당 하나, 먼저 끝난 순서대로 병합하고 나중 사람은 `main`을 다시 합친다.
- 마무리(한 명): 세 기능이 모두 병합되면 같은 질문("K-Digital Training 듣는 중 …")을 앱에서 확인하고 `eval.run_eval`로 검색 지표가 떨어지지 않았는지 본다.

- **완료 기준**: 위 질문에서 K-Digital Training이 추천에 없다. 이용 중 제도를 말하지 않은 질문들의 결과는 그대로다(`run_eval` 지표 변화 없음). 이용 중 제도 표현 5개 이상으로 테스트.

## 4. 검색·평가 개선

### R1. 상위 5개 중 틀린 제도 줄이기 (bad@5 0.297 → 낮추기)
- **현황**: 나쁨 사유 1위가 지역 불일치(`wrong_region` 88건), 다음이 무관한 제도(`irrelevant` 82건), 자격 불일치(`not_eligible` 52건).
- **1단계(분석)**: `run_eval`에 "상위 5개 중 나쁨 판정의 사유별 집계"를 추가해 어떤 원인이 큰지 숫자로 본다.
- **2단계(개선)**: 원인에 맞춰 지역 감점·필터, 허브 문서 노이즈 억제 등을 실험한다 (`python -m eval.sweep`, dev 시험지로만 튜닝).
- **완료 기준**: dev_v2에서 bad@5가 의미 있게 줄고(목표값은 1단계 후 정함), Hit@5·MRR이 떨어지지 않는다.
- **건드릴 곳**: `eval/run_eval.py`, `eval/sweep.py`, `src/retrieve/`.
- **규모**: 1단계 작음 / 2단계 중

### R2. 근거 없는 질문에 "모른다"고 답하기
- **현황**: 근거 없음 질문 4개에서 검색이 빈 결과를 낸 비율이 0%다. 최근 생성 단계에서 "해당 없음으로 본 제도만 남으면 근거 없음" 처리가 추가됐으니 그 위에서 검색 단계의 관련도 하한선을 정한다.
- **완료 기준**: 근거 없음 질문의 빈 결과율이 오르고, 근거 있는 질문의 Hit@5가 떨어지지 않는다. (근거 없음 질문이 더 필요하다: 독립 검색 3회 확인 기록이 있는 것만 인정.)
- **건드릴 곳**: `src/retrieve/hybrid.py`, `eval/run_eval.py`.
- **규모**: 중

### R3. 결혼·신혼집 질문(q13, q14)처럼 모든 방식이 놓치는 질문
- **현황**: 정답 제도 5개가 두 질문에서 같다. 질문 표현과 제도 텍스트의 어휘 차이일 가능성이 크다.
- **완료 기준**: 먼저 정답 제도들이 정말 질문에 맞는지 사람이 다시 확인한다. 맞다면 질문 확장·제도명 별칭 같은 방법을 실험하고 dev_v2에서 Hit@5 변화를 적는다.
- **규모**: 작음~중

## 5. 검수·평가 데이터

### D1. 새 질문 11개 판정하고 test 묶음 만들기
- **현황**: 질문 50개를 등록했지만 11개는 판정이 없다. 모든 평가 질문이 dev라 튜닝에 쓴 질문으로 최종 점수를 내고 있다.
- **할 일**: `python -m app.review_mode`에서 11개 판정 → `python -m src.review queue`로 미판정 후보 채우기 → 질문을 더 늘려 test 묶음 확보(100~300개 목표) → test는 마지막에 한 번만 `export --split test`.
- **완료 기준**: `stats`에서 conflict 0, test 질문이 10개 이상, `unjudged_rate@5` 0.1 이하 유지.
- **규모**: 사람 시간이 필요한 작업

### D2. 답변 평가 (일반 LLM vs 우리 서비스)
- **할 일**: 위 개선 후 `python -m eval.rag_compare`로 같은 질문·같은 채점기 비교 결과를 만들어 발표 근거로 쓴다. 앱에서 발견한 문제는 검수 화면 "시스템 답변 검수"에 메모로 남긴다(현재 메모 0건).
- **규모**: 중 (API 비용 발생, 실행 전 질문 수 확인)

### D3. 시험지·결과 파일 관리
- `eval/results/*.json`(파일당 약 1,900줄)을 저장소에 계속 올릴지 팀에서 정한다. 빼기로 하면 `.gitignore`에 추가.
- 시험지(`reviews/exports/dev_v2.jsonl`)는 판정이 바뀔 때만 다시 만들어 올린다.

## 7. 추천 순서

1. **W3 조사**(신청 URL 필드 확인)와 **R1 1단계**(나쁨 사유 집계)를 먼저 한다. 둘 다 결과를 보고 나머지를 정할 수 있다.
2. **W1**(이미 이용 중 제외)과 **W2**(금액 자세히)는 서로 다른 파일을 주로 고치므로 동시에 해도 된다 (`generator.py`는 둘 다 건드릴 수 있어 먼저 알린다).
3. **D1**은 사람 시간이 필요하므로 코드 작업과 병행한다.
4. 개선이 모이면 **D2**로 같은 질문 세트에서 전후를 비교하고, **X4**에 기록한다.
